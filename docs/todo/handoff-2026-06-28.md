## 1. Snapshot

NeNe Clear is a self-hosted payment-reconciliation + dunning product on the NENE2
framework (PHP 8.4, PHPStan L8; React + TS + Vite frontend). Scope is **入金消込・
督促管理 only** — not invoicing (see [ADR 0009](../adr/0009-separate-from-nene-invoice.md),
[scope-contract](../explanation/scope-contract.md)).

Two bodies of work landed this cycle:

- **Adoption Readiness milestone** (from the 2026-06 review #190) — substantially
  complete. The 2026-06 adoption review found the product + UI strong but adoption
  blocked by distribution / connectivity / operations. The engineering-ownable
  slice is shipped.
- **MFA (TOTP)** — backend **functionally complete** (enrolment + login
  enforcement). Frontend + break-glass CLI remain (slice 4).

Branch hygiene: local is `main`-only; all work merged.

## 3. MFA — state and remaining work

**Decision basis:** auth is federated (Suite = IdP), and MFA/TOTP is a NENE2-generic
capability, so Clear ships **standalone TOTP MFA** now, decoupled from federation
(nene-suite#341, ADR 0025; NENE2 `howto/totp-authentication` recipe, reference impl
`NENE2-FT/totplog`). Secrets are encrypted at rest with the #207 `Encryptor`;
recovery codes are stored hashed (one-way).

| Slice | What | Status |
| --- | --- | --- |
| 1 | TOTP foundation — RFC 6238 generator (verified vs reference vector), `totp_secrets`/`used_totp_steps`/`recovery_codes` + migration, `TotpAuthenticator` (lockout + replay), `RecoveryCodeService` | ✅ PR #213 |
| 2 | Self-service enrolment — `POST setup` / `POST enable` (→ 10 recovery codes) / `GET status` / `DELETE disable` (TOTP or recovery code) | ✅ PR #216 |
| 3 | Login-flow integration — password → `{ mfa_required, mfa_token }` → `POST /admin/auth/login/mfa` → token; challenge token signed with a derived secret (cannot be a bearer token) | ✅ PR #217 |
| 4 | **Frontend + ops** | ⬜ TODO |

**Slice 4 (remaining):**

- **Frontend** — an MFA section in Settings: enrol (show the `otpauth://` URI as a
  QR + the Base32 secret, confirm with a code), display/print the recovery codes
  once, show status + remaining recovery codes, disable. A **login challenge screen**
  for the `{ mfa_required, mfa_token }` response (prompt for a TOTP/recovery code,
  POST to `/admin/auth/login/mfa`).
- **Break-glass CLI** — an audited command to disable a user's MFA for lockout
  recovery (operator-run, server-side). Required before MFA can be recommended in
  production, or a locked-out sole admin is unrecoverable.

**Key code:** `src/Mfa/*` (generator, repos, authenticator, enrol use cases +
handlers, `MfaServiceProvider`), `src/Auth/MfaChallengeTokens.php` +
`VerifyMfaLoginUseCase` (login leg 2). API surface for the frontend:
`POST /admin/auth/totp/{setup,enable}`, `GET|DELETE /admin/auth/totp`,
`POST /admin/auth/login/mfa`. Problem slugs: `totp-invalid-code` (401),
`totp-locked` (423), `totp-not-enabled` (409), `totp-already-enabled` (409),
`mfa-challenge-invalid` (401).

**Not built (deliberate):** deployment-wide "require MFA" enforcement (forcing
un-enrolled users to enrol) — needs an enrol-grace flow; defer until requested.

## 4. Open challenges / risks

- **Dunning tone (ADR 0011 / scope X10).** The staged `reminder`/`final` templates
  (`lang/*.php`, PR #210) are conservative drafts flagged for professional review;
  do not strengthen tone without that review. No threatening language.
- **MFA lockout recovery.** Until the break-glass CLI ships (slice 4), do not
  enable MFA for a sole-admin deployment — a lost authenticator + spent recovery
  codes = lockout.
- **Real Invoice upstream not exercised.** `InvoiceUpstreamHttpClient` + contract
  tests exist but have never run against a live Invoice API (the API is still
  spec-only; see [invoice-upstream-contract](../integrations/invoice-upstream-contract.md)
  and the `invoice-side-defined-via-handoff-doc` memory). Treat upstream as
  spec-only; never edit `nene-invoice`.
- **Distribution / managed offering** is the real adoption pay-lever and is a
  product-owner decision, not a code task (see the [adoption review](../explanation/adoption-review-2026-06.md)).
